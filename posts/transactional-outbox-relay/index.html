고객에게는 결제 승인 내역이 있는데, 판매자는 주문을 확인할 수 없는 문제가 있었습니다. 결제 서비스에서는 승인이 끝났지만 주문은 여전히 결제 대기에 머물러 있었습니다. 판매자가 주문을 확인하고 수락하려면 주문 서비스에도 결제 결과가 반영되어야 했습니다.

이 상태에서 고객에게 다시 결제하도록 안내하면 중복 결제로 이어질 수 있습니다. 먼저 해야 할 일은 기존 결제 결과를 확인하고, 성공한 결과가 주문에 반영되지 않은 구간을 찾는 것이었습니다.

해결해야 할 문제는 세 가지였습니다. 확정된 결제 결과를 다시 찾을 수 있는가, 다음 발행이 불필요하게 기다리지 않는가, 같은 결과가 여러 경로로 와도 주문을 한 번만 변경하는가. Outbox 저장, Relay 실행 방식, 주문 반영 트랜잭션을 각각 이 질문에 맞춰 살펴봤습니다.

1. 결제는 됐다는데, 주문은 어디 갔을까

손님은 결제했다는데, 들어온 주문이 없어요.

판매자의 문의를 받고 처음에는 주문 목록이 갱신되지 않은 문제를 의심했습니다. 그런데 주문 조회 API에서도 해당 주문은 결제 대기였습니다. 화면을 새로고침해서 해결할 일이 아니었습니다.

같은 주문번호로 APM과 요청 로그를 따라갔습니다. 결제 서비스에는 PG 승인 성공과 결제 결과 저장이 남아 있었습니다. 반면 주문 서비스에는 그 결과를 반영한 기록이 없었습니다. 결제 서비스의 성공 로그에서 조사를 멈췄다면, 고객과 판매자는 계속 서로 다른 화면을 보고 있었을 겁니다.

확인 대상 같은 주문을 확인한 결과
결제 서비스 승인 성공 결과가 저장됨
주문 서비스 결제 대기 상태가 남아 있음
판매자 주문을 확인하고 수락할 수 없음

결제가 성공한 시점과 주문 처리가 끝난 시점 사이에 빈틈이 있었습니다. 그 구간을 찾기 위해 요청이 지나가는 서비스와 트랜잭션 경계를 살펴봤습니다.

여러 축제의 여러 푸드트럭이 같은 플랫폼을 사용하고, 고객은 QR로 메뉴를 열어 주문합니다. 주문은 고객의 결제 결과가 반영되어야 판매자가 확인하고 수락할 수 있습니다.

주문 기능을 배포할 때 진행 중인 결제 처리에 미치는 영향을 줄이기 위해 주문 서비스와 결제 서비스의 배포 단위를 분리했습니다. 두 서비스는 같은 MySQL 인스턴스를 사용하며 각자 소유한 테이블과 독립적인 트랜잭션을 관리합니다.

결제 서비스 담당 범위: 고객 결제의 승인과 취소, 환불 및 판매자별 정산과 지급대행.

정상 경로에서는 주문 서비스가 결제 서비스의 동기 HTTP API를 호출합니다. 결제 서비스가 PG 승인을 처리하고 성공 응답을 반환하면, 주문 서비스는 자기 트랜잭션에서 결제 확인 후 판매자 수락 대기를 기록합니다. 이후 판매자가 주문 수락을 누릅니다.

그런데 결제 결과를 커밋한 직후 HTTP 응답이 유실되거나, 주문 서비스가 응답을 받고 DB에 반영하기 전에 종료되면 두 상태가 갈라질 수 있습니다. 같은 MySQL을 사용해도 서비스 사이의 HTTP 호출이 하나의 로컬 트랜잭션으로 묶이지는 않습니다.

응답 타임아웃만으로 결제 실패를 확정하거나 새 결제를 요청할 수는 없습니다. 이미 승인된 결제라면 기존 결과를 주문에 반영해야 합니다. 따라서 HTTP 응답을 놓쳐도 확정된 결제 결과를 다시 전달할 경로가 필요했습니다.

2. HTTP 응답을 놓쳐도 결제 결과를 다시 전달할 수 있어야 한다

HTTP 응답을 놓치더라도 결제 결과 이벤트가 도착하면 주문을 반영할 수 있습니다. 그래서 기존 구현은 결제 결과를 커밋한 뒤 @TransactionalEventListener(AFTER_COMMIT)에서 Kafka로 이벤트를 발행했습니다.

기존 흐름에서 필요한 부분만 남기면 다음과 같습니다.

@TransactionalEventListener(phase = TransactionPhase.AFTER_COMMIT)
public void onPaymentConfirmed(PaymentConfirmed event) {
    kafkaTemplate.send("payment-events", event.paymentId(), event);
}

AFTER_COMMIT은 결제 트랜잭션이 성공한 뒤 리스너를 실행하게 합니다. 리스너 실행과 Kafka 기록을 결제 DB의 커밋에 묶어 주지는 않습니다. send()가 반환한 future를 수집하지 않으면 이후 전송 실패도 이 메서드의 정상 반환만으로는 알 수 없습니다. Spring의 트랜잭션 이벤트 실행 시점

하지만 코드를 따라가면 DB 커밋 이후, Kafka 발행 이전에 빈틈이 있었습니다. 이 구간에서 프로세스가 종료되면 결제 결과는 DB에 남지만 발행할 일은 메모리와 함께 사라집니다. HTTP 반영도 놓친 주문은 이벤트로 복구할 기회까지 잃을 수 있었습니다.

여기에 .get()을 붙여 ACK를 기다리더라도 이미 끝난 결제 커밋을 되돌릴 수는 없습니다. 반대로 커밋 전에 Kafka에 보내면 결제 DB가 롤백됐는데 승인 이벤트는 남을 수 있습니다.

발행 위치 중간에 실패했을 때 남을 수 있는 상태
결제 DB 커밋 전 Kafka 전송 결제 결과는 롤백됐지만 이벤트는 전달됨
결제 DB 커밋 후 Kafka 전송 결제 결과는 남았지만 이벤트는 전달되지 않음
결제 결과와 Outbox를 같은 TX로 저장 커밋된 결제 결과에 대응하는 발행 의도를 DB에서 다시 찾음

문제는 동기 전송과 비동기 전송 중 무엇을 골랐느냐가 아니라, 프로세스가 사라진 뒤에도 다시 보낼 대상을 찾을 수 있느냐였습니다.

발행 시도 로그가 있다고 해결되는 문제도 아니었습니다. 로그만으로는 Kafka의 ACK를 받았는지, 주문 서비스가 적용했는지 알 수 없습니다. 프로세스가 재시작한 뒤 무엇을 다시 보내야 하는지 DB에서 찾을 수 있어야 했습니다.

3. 결제 결과와 발행할 이벤트를 함께 저장해야 한다

결제 결과와 Outbox 이벤트를 같은 결제 서비스의 로컬 트랜잭션으로 저장하도록 바꿨습니다. 둘 중 하나라도 실패하면 함께 롤백합니다. 이제 결제 결과가 커밋됐다면 발행할 이벤트도 DB에 남습니다. Relay는 미발행 행을 읽어 Kafka로 전달하고 결과를 기록합니다.

여기서 같은 TX에 포함되는 것은 결제 결과와 Outbox입니다. 주문 상태 변경은 주문 서비스의 별도 TX이며, 외부 PG 승인도 이 DB 트랜잭션에 포함되지 않습니다. PG 승인 뒤 DB 기록에 실패하거나 PG 응답을 놓친 경우에는 결제 서비스의 대사 배치가 거래 조회로 기존 결제 시도를 복구합니다.

이 변경으로 결제 서비스가 커밋 직후 종료되더라도 다음 프로세스가 남아 있는 Outbox를 이어서 발행할 수 있게 됩니다. 장애 복구의 출발점을 요청 로그에서 DB에 저장된 발행 의도로 옮긴 것입니다.

커밋 경계와 중복 방지 경계를 함께 정해야 한다

트랜잭션 경계만 남긴 코드는 다음과 같습니다. 외부 PG 호출은 이 메서드가 시작되기 전에 끝나며, 여기에는 확인된 PG 결과를 전달합니다.

@Transactional
public ConfirmedPaymentResult recordResult(VerifiedPgResult pgResult) {
    var payment = payments.findByAttemptIdForUpdate(
        pgResult.paymentAttemptId());

    var existing = results.findByPgResultKey(pgResult.key());
    if (existing.isPresent()) {
        existing.get().verifySameFact(payment.id(), pgResult);
        return existing.get();
    }

    var result = payment.confirm(pgResult); // 업무 검증과 다음 순번 확정
    results.save(result);
    outbox.save(PendingPaymentEvent.from(result)); // ID와 payload 고정
    return result;
}

같은 원거래를 반영하는 모든 경로는 동일한 결제 행을 잠그도록 합니다. PG 결과 키는 PG사와 상점 등 식별자 범위를 포함해 충돌하지 않도록 정하고, 원거래와 금액이 기존 결과와 같은지도 확인합니다. 승인 이후 서로 다른 부분 환불 결과는 서로 다른 결과 키를 사용합니다.

DB의 PG 결과 키와 (payment_id, event_sequence) 유일성 제약은 마지막 방어선입니다. 유일성 충돌이 나면 실패한 TX를 롤백한 뒤 새 TX에서 기존 결과를 다시 조회하고 같은 사실인지 검증합니다. 다른 결제나 다른 금액의 충돌을 성공한 중복으로 바꾸지 않습니다. 위 코드는 이 재조회 바깥 경로를 생략한 핵심 흐름입니다.

eventId와 payload는 결과를 기록할 때 한 번 정해 저장합니다. Relay는 저장된 값을 그대로 읽습니다. 재발행할 때 새 ID를 생성하거나 현재 결제 객체에서 payload를 다시 만들면, 같은 사건을 재전달한다는 계약이 깨집니다. Outbox 저장에 REQUIRES_NEW를 사용하거나 AFTER_COMMIT에서 별도로 INSERT하면 결제 결과와의 원자성도 사라집니다.

중단 지점에 따라 DB에서 다시 찾을 대상과 복구 책임이 달라집니다.

중단 지점 남는 상태와 복구 책임
결제 결과와 Outbox의 커밋 전 두 변경 모두 롤백됩니다. PG 승인 여부는 결제 서비스가 기존 시도를 조회해 확인합니다.
커밋 후, Kafka 전송 전 PENDING을 Relay가 다시 조회합니다.
Kafka ACK 후, PUBLISHED 커밋 전 같은 이벤트가 재발행될 수 있습니다. 주문 서비스가 업무 중복을 막습니다.
PUBLISHED 커밋 후, 주문 반영 전 Relay의 발행은 끝났습니다. Consumer lag와 보류 이벤트, 주문 반영 오류를 확인합니다.

도입 전에 이미 누락된 이벤트에는 Outbox 행이 없습니다. 기존 미반영 주문까지 복구하려면 확정 결과와 주문 적용 이력을 대조하는 별도 경로가 필요합니다. 당시의 불변 결과를 재구성할 수 있는 대상만 원래 결과 식별자로 연결해야 하며, 현재 결제 상태에서 과거 승인 이벤트를 추측해 만들지는 않습니다. Outbox 도입 이후의 재전달과 도입 이전 누락의 복구는 구분해야 합니다.

따라서 PUBLISHED는 Kafka 전송 완료를 기록했다는 상태입니다. 주문 반영 완료나 판매자 화면 노출까지 뜻하지 않습니다. Outbox가 남아 있고 Relay와 Consumer가 재개되며 오류를 복구한다는 조건도 필요합니다. Outbox 행을 저장하는 것만으로 후속 업무가 저절로 완료되지는 않습니다.

이벤트에는 후속 처리가 필요한 업무 사실과 식별자를 넣습니다.

{
  "eventId": "event-101",
  "eventType": "PaymentSucceeded",
  "schemaVersion": 1,
  "eventSequence": 1,
  "occurredAt": "2026-11-06T03:00:00Z",
  "orderId": "order-101",
  "paymentAttemptId": "attempt-101",
  "paymentId": "payment-101",
  "amount": 18000,
  "currency": "KRW"
}

schemaVersion은 이벤트 형식의 버전이며, eventSequence는 같은 결제에서 발생한 결과의 순서입니다. 두 값의 역할은 다릅니다. 승인과 승인 취소, 환불처럼 주문에 반영할 결과를 payment-events 토픽에 전달하고, Kafka key는 paymentId로 통일합니다. PaymentCancelled는 취소 요청이 아니라 PG에서 승인 취소가 완료됐다는 결과입니다. 환불 완료 결과에는 개별 환불을 식별할 refundId와 환불 금액도 필요합니다.

금액은 통화의 최소 단위 정수로 표현합니다. PG의 승인 거절이 확정되면 PaymentFailed를 기록합니다. 응답 타임아웃으로 결과가 불확실하면 UNKNOWN으로 확인을 계속하며, 실패 이벤트를 성급히 만들지 않습니다. 카드 번호와 PG 인증 정보는 payload에 넣지 않습니다.

PaymentSucceeded가 전달하는 것은 특정 결제 시도가 특정 금액으로 승인됐다는 확정 사실입니다. 따라서 payload에는 이벤트 발생 시점의 결제 결과를 담습니다. 결제 객체 전체의 스냅샷이 필요한 것은 아니며, 해당 사실을 해석하고 주문에 적용하는 데 필요한 식별자와 금액, 통화 등을 남깁니다.

Zero Payload로 식별자만 전달하는 방식도 가능합니다. 다만 결제 ID로 현재 상태만 조회하면, 승인 뒤 환불이 진행된 경우 당시 승인 결과를 그대로 얻을 수 없습니다. 같은 의미를 전달하려면 식별자로 그 시점의 불변 승인 내역을 조회할 수 있어야 합니다. 이번에는 결제 서비스의 조회 API가 응답하지 않아도 주문 반영을 이어갈 수 있도록, 확정 결과를 이벤트에 직접 담았습니다. 이벤트 알림과 데이터를 포함한 이벤트의 차이

취소와 환불 이벤트에는 원거래와 변경 범위를 담아야 한다

부분 취소가 가능하다면 paymentId만 보고 “이미 환불된 결제”로 처리할 수 없습니다. 같은 원승인에 첫 번째 5,000원 환불과 두 번째 3,000원 환불이 각각 발생할 수 있기 때문입니다. 원주문은 orderId, 원승인 결제는 paymentId, 이번 취소와 환불 작업은 refundId로 구분합니다. PG의 원승인 거래 ID와 이번 취소 거래 ID도 별도로 연결합니다.

다음은 18,000원 결제에서 5,000원 부분 취소가 완료된 내부 이벤트입니다. PaymentCancelled는 전체 주문 취소라는 뜻이 아니라 PG 승인 취소가 완료됐다는 결제 사실을 나타냅니다.

  "eventSequence": 2,

refundAmount는 이번 건의 금액이며, refundedAmountTotal과 remainingAmount는 이 순번의 결과를 확정한 시점의 누적 금액과 잔액입니다. 누적 금액을 다시 더하지 않습니다. 이후 3,000원이 추가 환불되면 새로운 refundId와 다음 순번으로 이번 환불 금액 3,000원과 누적 환불액 8,000원, 잔액 10,000원을 전달합니다. 같은 refundId의 재수신은 중복이지만, 다른 refundId의 부분 환불은 별도로 반영해야 합니다. 금액 검증은 같은 결제에 대한 확정 내역을 기준으로 직렬화하고, 환불 결과와 잔액, 순번, Outbox를 같은 결제 TX에서 기록합니다.

주문 서비스는 취소할 주문 항목 ID와 수량, 할인 배분을 반영한 환불 금액을 불변의 주문 변경 내역으로 저장하고, 그 식별자인 orderAdjustmentId를 결제 서비스에 전달합니다. 이벤트를 받은 주문 서비스는 자기 DB의 변경 내역과 원주문과 원결제를 대조합니다. 결제 서비스가 주문 테이블을 직접 읽지 않아도 어떤 메뉴 몇 개에 대한 취소인지 연결할 수 있습니다. 주문 항목 취소 없는 금액 보상은 수량 취소와 구분합니다.

NICEPAY 취소 API도 원승인의 tid와 취소 결과의 cancelledTid를 구분하고, balanceAmt로 취소 후 잔액을 제공합니다. 부분 취소 요청의 PG orderId는 요청별 고유값을 사용하도록 되어 있으므로, 내부 원주문 orderId를 모든 부분 취소에 그대로 재사용하지 않고 refundId에 연결한 요청 식별자로 매핑합니다. 응답을 놓쳤다면 기존 환불 요청을 조회하고 대조해 복구하며 새 환불로 무조건 재호출하지 않습니다. NICEPAY 취소와 환불 API

대사 배치는 결제 서비스 안에 유지했습니다. 1분마다 결과가 미확정인 결제 시도를 찾아 PG 거래를 조회하고, 결과가 새로 확정되면 결제 결과와 Outbox를 같은 로컬 트랜잭션에 저장합니다. 정상 승인 응답으로 결과를 확정한 경우와 이후 전달 경로는 같습니다.

이렇게 대사 배치는 PG와 결제 서비스 사이의 결과 불일치를 복구하고, Outbox는 결제 서비스에서 확정한 결과를 주문 서비스로 전달하는 역할을 맡습니다. 이미 결과가 확정된 결제는 다음 대사 실행을 기다리지 않고 Relay가 전달하며, PG 결과가 불확실한 결제는 조회로 확인한 뒤 전달합니다.

4. 지연되어서 좋은 데이터는 없다.

Outbox 도입으로 전달할 일이 사라지는 문제를 막았지만, 주문이 몰리는 시간에는 판매자가 주문을 뒤늦게 확인하는 상황이 남았습니다. 결제를 마친 고객이 먼저 확인을 요청하고, 판매자 화면에는 주문이 한 박자 늦게 나타나는 일이었습니다.

이번에는 결제 결과와 Outbox가 모두 DB에 남아 있었습니다. 복구할 이벤트가 없는 문제가 아니라 저장된 이벤트가 언제 전송되기 시작하는지의 문제였습니다. 한 번에 유입되는 양이 Relay가 처리하는 양보다 많거나, 앞선 회차가 느린 전송을 기다리는 동안에는 다음 이벤트의 대기가 누적될 수 있었습니다.

HTTP 응답으로 주문을 반영하지 못한 건은 Relay가 결과를 전달해야 판매자가 확인할 수 있습니다. 따라서 PG 승인이 느린 문제와, 승인은 이미 끝났는데 다음 전달 단계가 시작되지 않는 문제를 나눠 봐야 했습니다.

같은 orderId와 paymentAttemptId, eventId로 결제 커밋 완료, Relay의 조회와 send 시작, Kafka 전송 완료, 주문 반영 커밋 시점을 연결하면 대기를 다음처럼 구분할 수 있습니다.

구간 지연이 길 때 확인할 대상
승인 요청 → 결제 결과 확정 PG 응답과 HTTP 통신과 호출 제한 대기
결제 결과 커밋 → Relay send 시작 폴링 간격, 이전 회차의 대기, 가용 슬롯, 선행 이벤트 보류
send 시작 → 전송 완료 metadata나 buffer 대기, Kafka ACK 대기와 내부 재시도
Kafka 전달 → 주문 반영 커밋 Consumer 적체, 선행 결과 대기, 주문 DB 처리

Outbox의 created_at은 INSERT 시각이지 커밋 완료 시각은 아닙니다. 정확한 반영 구간을 보려면 커밋 이후 관측 시각을 구분하고 서비스 간 시계 차이도 관리해야 합니다. PENDING이 오래 남았다는 사실만으로 Kafka 미전달이라고 단정하지 않습니다. 이미 전달됐지만 PUBLISHED 기록이 늦은 건도 있고, HTTP로 주문 반영이 끝난 건도 있습니다.

5초 fixedDelay가 매 5초 조회를 뜻하지는 않았다

기존 Relay는 최대 100건을 읽고 전송을 시작한 뒤, 그 회차의 future를 공통 마감까지 수집하고 결과를 한 번에 기록했습니다. 스케줄러가 이 메서드를 끝내야 다음 fixedDelay가 시작됐습니다. 따라서 실제 조회 간격에는 설정한 5초뿐 아니라 조회와 전송 등록, 전체 결과 수집, DB 기록에 걸리는 시간까지 더해졌습니다. Spring의 fixedDelay 동작

@Scheduled(fixedDelay = 5000)
public void relayOnce() {
    var events = reader.findDue(100); // 짧은 읽기 TX
    var futures = sender.sendAll(events); // 먼저 비동기 전송 시작
    var outcomes = collectUntilSharedDeadline(futures);
    resultRecorder.recordBatch(outcomes); // 별도의 쓰기 TX
} // 여기서 반환한 뒤 5초를 더 기다립니다.

한 회차에 100건만 읽고 그 뒤 5초를 쉬면, 이 경로의 지속 발행량은 처리 시간이 0이어도 초당 20건을 넘기기 어렵습니다. Kafka와 DB가 처리할 여유가 있어도 다음 조회를 시작하지 않으면 활용할 수 없습니다. 새로 쌓이는 속도가 발행 속도보다 빠른 동안에는 다음 회차의 대기량도 계속 늘어납니다.

조회 한 회차의 시작 간격은 다음처럼 분해할 수 있습니다.

기존 시작 간격
= 조회 + send 등록 + 배치 결과 대기 + 결과 일괄 기록 + fixedDelay

개선 후 시작 간격
= 조회 + send 등록 + fixedDelay

첫 조정은 폴링 사이의 빈 대기를 줄이는 것이었습니다. 조회 간격을 짧게 조정했을 때, 정상 HTTP 응답을 놓쳐 이벤트로 복구하는 주문의 반영 지연은 운영 당시 회고 기준으로 다음과 같이 달라졌습니다.

대상 조회 주기 조정 전 조정 후
결제 결과 확정 → 주문 반영 DB 커밋 약 5초 약 200ms

두 값은 운영 당시 회고에 따른 근사값이며, 평균이나 p95로 집계한 수치는 아닙니다. 약 200ms는 0.2초입니다. 이 결과에서 말할 수 있는 것은 HTTP 반영을 놓친 주문이 다음 전달을 기다리는 시간을 줄였다는 것까지입니다. 전체 결제의 처리량이나 최대 부하를 이 표로 설명하지 않습니다.

PG 승인 대기와 판매자 수락 시간은 이 값에 포함하지 않습니다. 판매자 화면까지의 시간은 조회와 화면 갱신, 알림에 걸리는 시간도 더해집니다. 이 수치를 콜백 방식 자체의 개선 폭으로 해석해서도 안 됩니다. 조회 주기를 줄여 발견 대기를 줄이는 일과, 배치의 느린 한 건이 다음 조회를 막는 구조를 바꾸는 일은 별도 개선이었습니다.

개선 전후의 반영 지연과 미반영 건수를 함께 비교하기

회고 수치와 별도로, 폴링 주기 변경의 영향을 같은 조건에서 측정한 결과도 비교했습니다. 로컬 MySQL 8.4와 Kafka 4.1.2 단일 브로커, 모의 PG를 사용하는 HTTP 경로에서 조건당 200건씩 3회 측정했습니다. 주문 서비스와 결제 서비스는 별도 HTTP 서버와 DB 트랜잭션으로 동작합니다. 동일 JVM의 단조 시계로 결제 커밋 완료 확인 시점과 주문 커밋 완료 확인 시점을 기록했습니다. 실제 PG나 운영 환경의 측정값은 아닙니다.

반영이 끝난 주문의 분위수와 함께, 아직 반영되지 않은 주문이 얼마나 쌓였는지도 확인했습니다. 다음 값은 실행마다 20ms 간격으로 관측한 최대치의 중앙값입니다. 관측 사이의 순간 최대치를 보장하지는 않습니다.

PG가 느린 조건에서는 폴링을 줄여도 요청부터 반영까지 p95가 약 4.25초 남았습니다. Relay가 줄이는 것은 결제가 확정된 뒤의 전달 대기이며, PG 승인 대기까지 없애 주지는 않습니다. 판매자 화면 갱신과 실제 수락까지 걸리는 시간도 위 구간에 포함하지 않았습니다.

5. 느린 한 건이 다른 결제의 발행을 막지 않도록 해야 한다

기존 코드도 먼저 여러 건의 send를 시작했으므로 Kafka 전송이 한 건씩만 진행된 것은 아닙니다. 문제는 완료를 수집하는 스케줄러가 배치 전체에 묶여 있었다는 점입니다. 예를 들어 100건 중 99건이 끝나도 나머지 1건의 전송이 늦으면, 다음 Outbox를 읽는 작업은 그 회차가 끝날 때까지 시작되지 않았습니다.

이미 Kafka에 전달된 99건은 기존 방식에서도 Consumer가 바로 반영할 수 있었습니다. 콜백으로 줄이려는 대기는 그 99건의 주문 반영이 아니라, DB에 새로 쌓인 다음 이벤트의 전송 시작 대기였습니다. get을 whenCompleteAsync로 바꾸는 것뿐 아니라, 스케줄러가 기다리는 범위를 바꿔야 했습니다.

전송과 완료 처리 방식 동시에 진행될 수 있는 전송 다음 조회가 시작되는 조건
각 send().get() 후 다음 전송 이 루프에서는 한 건 선택한 모든 이벤트의 ACK와 결과 기록 완료
먼저 모두 send(), 이후 future 수집 여러 건 선택한 배치의 결과 수집과 일괄 기록 완료
슬롯을 제한한 완료 콜백 남은 슬롯 범위의 여러 건 조회와 전송 등록 후 반환하고, 다음 스케줄에서 빈 슬롯만 조회

기존 방식은 두 번째였습니다. 이미 전송을 병렬로 시작하고 있었으므로 “동기를 비동기로 바꿔 빨라졌다”고 설명하면 원인을 잘못 짚게 됩니다. 바꾼 것은 전송 API보다 스케줄러의 종료 조건과 결과 기록 단위였습니다.

Relay는 단일 활성 스케줄러와 완료 콜백으로 구성합니다. 조회와 전송을 시작하는 스케줄러는 하나이며, 전송 완료와 DB 결과 기록은 그 스케줄러가 반환한 뒤에도 진행될 수 있습니다. 배포나 장애로 발행 역할을 인계할 때 다른 프로세스가 동시에 발행하지 않는 조건입니다. 여러 프로세스가 동시 발행하려면 DB 선점과 lease, token을 별도로 설계해야 합니다.

  1. 읽기 TX: 재시도 시각이 지난 PENDING 중 결제별 맨 앞의 미발행 이벤트만 고릅니다. 이 프로세스가 처리 중인 ID를 제외하고, 남은 처리 슬롯만큼 최대 100건 조회합니다.
  2. TX 밖: 조회한 ID와 슬롯을 예약한 뒤 send()를 시작합니다. Kafka 응답을 기다리며 DB TX를 유지하지 않습니다.
  3. 완료 콜백: 각 전송이 끝나면 별도 실행기에서 결과 기록을 시작합니다.
  4. 쓰기 TX: 해당 이벤트의 PUBLISHED 상태나 재시도 시각, 격리 상태를 저장합니다. 커밋이 끝난 뒤에만 처리 중 ID와 슬롯을 반환합니다.

개선 후 스케줄러는 ACK를 기다리지 않고 조회와 전송 등록만 마치고 반환합니다. 흐름을 축약하면 다음과 같습니다. poll-delay는 설정으로 분리하며 코드의 100ms는 설정 예입니다. reader의 조회 TX와 결과 기록 TX는 서로 다른 빈의 프록시를 통해 실행합니다.

@Scheduled(fixedDelayString = "${outbox.relay.poll-delay-ms:100}")
public void relayOnce() {
    int free = inFlight.remainingCapacity();
    if (free == 0) return;

    var events = reader.findDueHeads(
        Math.min(fetchLimit, free), inFlight.eventIds());

    for (var event : events) {
        if (!inFlight.tryReserve(event.eventId())) continue;
        sender.sendAndTrack(event);
    }
} // ACK와 결과 기록을 기다리지 않고 반환합니다.

한 회차의 종료 조건이 달라졌으므로 다음 조회까지의 간격에서 전체 ACK 대기와 결과 일괄 기록이 빠집니다. 다만 조회와 send 등록에 걸리는 시간은 남습니다. 비동기 send도 metadata나 버퍼를 기다릴 수 있으므로, 설정한 poll-delay가 정확한 실행 주기라는 뜻은 아닙니다.

sendAndTrack()에서는 전송별 완료를 결과 기록 실행기에 연결합니다. 아래는 핵심 흐름이며 send의 동기 예외와 실행기 작업 거부는 completionTracker의 복구 경로로 넘깁니다.

var sendFuture = kafkaTemplate.send(toRecord(event));
var recordFuture = sendFuture.whenCompleteAsync((result, sendError) -> {
    try {
        // 다른 빈의 프록시를 통해 호출하며, DB 커밋 후 반환합니다.
        resultRecorder.recordInNewTransaction(event, result, sendError);
        inFlight.complete(event.eventId()); // 커밋 후 ID와 슬롯 반환
    } catch (RuntimeException dbError) {
        // 슬롯을 유지하고, 같은 전송 결과의 DB 기록만 재시도합니다.
        completionTracker.retryRecording(event, result, sendError, dbError);
    }
}, resultExecutor);

completionTracker.watch(event, sendFuture, recordFuture);

completionTracker는 원본 sendFuture의 결과와 DB 기록 오류를 구분해 보존합니다. whenCompleteAsync의 후속 future가 예외로 끝났다는 이유만으로 DB 기록 실패라고 판단하지 않습니다. 실행기 등록이 거부되면 원본 전송 결과를 회수해 DB 기록을 다시 예약하고, 신규 발행도 줄입니다. send 자체가 동기 예외를 던진 경우도 동일한 결과 기록 경로로 넘겨 슬롯을 잃지 않게 합니다.

Kafka에 보냈다고 Relay의 일이 모두 끝난 것은 아닙니다. ACK를 받은 뒤에도 Outbox에 PUBLISHED를 기록해야 합니다. whenCompleteAsync(..., resultExecutor)는 이 DB 작업을 별도 실행기에 넘기는 연결점입니다. Kafka 전송 완료 스레드에서 DB 응답까지 기다리지 않도록 합니다. Spring Kafka 전송 문서

여기서 슬롯은 아직 DB 기록까지 끝나지 않은 이벤트를 맡아 두는 자리입니다. Kafka 응답을 기다리는 동안에도, DB 작업이 밀려 기다리는 동안에도 같은 슬롯 하나를 차지합니다. DB 커밋이 끝나야 다음 이벤트에 자리를 내줍니다.

전체 한도가 100건이라고 가정해 보겠습니다. Kafka 결과 대기 60건과 DB 기록을 기다리거나 진행 중인 30건이 있다면, 다음 조회에서 새로 맡을 수 있는 양은 10건입니다. 조회 상한 100건과 전체 처리 한도는 별도 설정입니다. 전체 한도와 실행기 큐와 DB 연결 수를 함께 제한해야 DB가 느릴 때도 작업이 끝없이 쌓이지 않습니다.

이 구조에서는 완료된 건부터 슬롯을 돌려받고 다음 스케줄이 그만큼만 추가로 보냅니다. Kafka 전송만 세면 DB 기록이 밀리는 동안 무제한으로 새 전송을 시작할 수 있으므로, DB 기록 완료까지 슬롯에 포함합니다. 배치당 한 번이던 결과 커밋을 건별로 나누는 만큼 DB 쓰기 횟수는 늘어납니다. 결과 실행기의 스레드 수와 큐 용량, DB 연결 수도 함께 제한해야 합니다.

같은 이벤트를 다시 조회하지 않도록 send 전에 ID를 처리 중 집합에 등록하고, 이후 조회에서 제외합니다. DB에는 아직 PENDING이어도 이 프로세스가 맡고 있는 행입니다. 단일 활성 스케줄러에서는 이 집합을 메모리로 관리하고, DB 커밋 후에만 ID와 슬롯을 반환합니다.

실패했을 때는 실패한 단계부터 다시 처리합니다.

  • Kafka 전송 성공 후 DB 기록 실패: 전송 결과와 슬롯을 유지하고 DB 기록만 백오프로 재시도합니다. 이때 슬롯을 먼저 반환하면 같은 PENDING 행을 다시 전송할 수 있습니다.
  • Kafka 전송의 재시도 가능한 최종 오류: 다음 발행 시각을 DB에 기록합니다. 그 커밋이 끝나면 슬롯을 반환하고, 재시도 시각이 지난 뒤 같은 eventId로 다시 발행합니다.

배포할 때는 신규 조회와 전송 중지 → 진행 중인 전송과 후속 DB 기록 대기 → 결과 실행기 종료 순서를 지킵니다. 결과 실행기를 먼저 끄면, 뒤늦게 도착한 ACK를 DB에 기록할 곳이 없어집니다. 종료 유예 시간 안에 마치지 못한 행은 DB에 남겨 다음 프로세스가 재발행할 수 있게 합니다.

delivery.timeout.ms=30초는 Kafka 전송 시도의 완료 통보 상한입니다. DB 기록까지 30초 안에 끝난다는 뜻은 아닙니다. send() 자체의 metadata나 buffer 대기는 max.block.ms로 따로 봅니다. 임의의 짧은 감시 타임아웃만으로 슬롯을 반환하거나 같은 행을 다시 보내지 않습니다.

기본 전송 설정은 다음과 같습니다. 멱등 Producer를 명시적으로 활성화하고, 이에 필요한 ACK와 동시 요청 조건도 함께 맞춥니다.

acks=all
enable.idempotence=true
max.in.flight.requests.per.connection=5

Kafka의 멱등 Producer는 같은 파티션에 보내는 배치에 producer ID와 epoch, sequence를 사용합니다. 내부 재시도에서는 같은 배치의 sequence를 유지해 브로커가 중복 기록을 판별할 수 있게 합니다. 반면 Relay가 DB의 같은 행을 읽어 새 send()를 호출하면 새 전송으로 취급됩니다. eventId가 같다는 이유로 Kafka가 두 호출을 합치지는 않습니다. Kafka Producer의 배치 sequence 할당

콜백은 완료된 건부터 슬롯을 반환해 다른 결제의 다음 전송을 시작할 여유를 만듭니다. 다만 결과 기록이 느리면 슬롯 반환도 느려져 처리량에 영향을 줍니다. 같은 결제 안에서 지켜야 할 업무 순서는 별도로 제한합니다.

실패한 이벤트는 100ms마다 다시 보내지 않는다

한 번의 전송이 실패할 때마다 바로 Outbox 행을 갱신하고 새로 보내면, 짧은 Kafka 장애에도 DB 쓰기와 재발행이 늘어납니다. 짧은 오류는 Producer 내부에서 재시도하고, 그 전송 시도까지 실패한 경우에 Outbox의 다음 발행 시각을 미루도록 나눴습니다.

Kafka 응답이 늦어지면 ACK 대기와 내부 재시도가 길어지고, 전송이 끝나지 않은 이벤트가 처리 슬롯을 계속 차지합니다. send() 자체가 metadata나 버퍼를 기다리는 시간도 따로 제한해야 합니다. 이에 따라 재시도 간격과 한 전송의 완료 예산, 전송 등록 대기를 나눠 설정했습니다.

설정 선택한 값 선택 근거
retry.backoff.ms / retry.backoff.max.ms 100 / 1000ms 일시 오류의 첫 재시도는 빠르게 시작하되, 실패가 이어질 때는 간격을 늘려 같은 장애에 요청을 계속 몰아넣지 않도록 합니다.
delivery.timeout.ms 30초 기본 120초보다 한 전송의 재시도 예산을 줄입니다. 최종 실패를 기록한 뒤의 재전달은 Outbox 백오프로 넘깁니다.
max.block.ms 5초 기본 60초보다 전송 등록 대기를 줄입니다. 단일 스케줄러가 metadata 조회와 버퍼 확보 때문에 오래 멈추는 시간을 제한합니다.

이때 30초는 주문 반영의 목표 시간이 아니라, 장애 중 한 전송 시도에 허용하는 시간입니다. 정상 전송은 ACK를 받는 즉시 결과를 기록하고 슬롯을 반환합니다. 전송 타임아웃 뒤에도 Kafka에 기록됐을 가능성은 남으므로, 다시 발행할 때는 같은 eventId를 유지하고 Consumer가 중복을 막습니다. 설정 변경 후에는 재시도 건수뿐 아니라 처리 슬롯 점유, 가장 오래된 PENDING의 대기 시간, 주문 반영 지연을 함께 봤습니다. Kafka 프로듀서 설정

전송 시도가 최종 실패하면 Relay는 재시도 가능한 행의 attempt_count와 next_attempt_at을 결과 기록 TX에서 갱신합니다. 횟수는 Outbox의 새 전송 시도 기준이며 Kafka 내부 재시도 횟수와 다릅니다. BLOCKED는 잘못된 payload처럼 자동 재시도로 해결되지 않는 오류를 격리할 때 사용합니다. Kafka 장애나 단순 관측 타임아웃을 이유로 결제 결과 이벤트를 삭제하지 않습니다.

기본 조회 조건은 status = 'PENDING' AND next_attempt_at <= CURRENT_TIMESTAMP(6)이며, 현재 처리 중인 ID도 제외합니다. 신규 행은 생성 즉시 발행 대상이 되도록 초기 시각을 넣습니다. 다만 이 조건만으로는 같은 결제의 이벤트 순서를 지킬 수 없으므로, 선행 미발행 이벤트가 있는지도 함께 확인해야 합니다.

백오프 정책 예시로 기본 간격을 1초, 2초, 4초처럼 늘리되 최대 30초로 제한하고, 각 간격의 50–100% 범위에서 무작위로 대기 시간을 정할 수 있습니다. 같은 시점에 실패한 이벤트가 함께 몰려 재전송되는 것을 줄이기 위한 jitter입니다. 이벤트마다 Relay 스레드를 재우지 않고 다음 시각을 DB에 남깁니다. DB 기록 실패의 재시도와 Kafka 발행 실패의 재시도는 구분합니다.

행별 백오프만으로 Kafka 전체 장애 중 신규 이벤트의 발행 시도까지 억제되지는 않습니다. 광범위한 연결 실패에는 신규 전송을 잠시 줄이는 정책도 함께 고려합니다. 서킷브레이커를 추가하더라도 차단된 이벤트는 Outbox에 보존하고 복구 후 다시 전달해야 합니다. 오래 기다리는 이벤트와 반복 실패, 결과 기록 적체도 관측합니다.

백오프 중 같은 결제의 후속 이벤트가 추월하지 않도록 해야 한다

retry.backoff.ms가 조절하는 Producer 내부 재시도와, Relay가 나중에 새로운 send()를 호출하는 재발행은 구분해야 합니다. 앞의 멱등 Producer 설정은 같은 파티션에 제출한 레코드의 순서를 유지합니다. 그러나 Relay가 업무 순서와 반대로 제출한 이벤트까지 원래 순서로 바꿔 주지는 않습니다. Kafka의 재시도와 순서 보장

선행 이벤트를 건너뛰고 발행 가능한 행만 조회하면 다음 상황이 가능합니다.

시점 결제와 주문 처리 Outbox 전달
승인 완료 결제 서비스에 승인 저장, HTTP 응답으로 주문에도 승인 반영 승인 이벤트 A의 발행 실패, 백오프
고객 취소 기존 승인에 대한 PG 취소 완료 취소 이벤트 B가 먼저 발행됨
A 재시도 주문에는 이미 취소 결과가 반영됐을 수 있음 승인 이벤트 A가 뒤늦게 도착

이때 결제 서비스에는 실제 승인 내역이 있습니다. 주문 서비스가 승인 이벤트를 받기 전에 취소 이벤트를 받을 수 있다는 문제입니다. payment-events라는 토픽 하나를 사용하고 key도 같게 설정했더라도, B를 먼저 보내면 Kafka에는 B → A로 기록됩니다. A와 B는 서로 다른 eventId이므로 중복 검사도 모두 통과합니다.

따라서 같은 결제의 선행 이벤트가 미발행 상태라면 후속 이벤트는 보내지 않고, 다른 결제의 발행은 계속하도록 합니다. eventSequence는 이 토픽에 전달하는 주문 반영용 결과에 대해 paymentId별로 1부터 연속 증가시킵니다. 정산과 지급대행의 다른 이벤트까지 같은 순번에 섞지 않습니다. 같은 결제 행의 갱신을 직렬화하고, 순번 증가와 결제 결과 저장, Outbox INSERT를 같은 로컬 TX로 커밋합니다. (payment_id, event_sequence)에는 유일성 제약을 둡니다. 생성 시각이나 Outbox의 전역 ID만으로 업무 순서를 추정하지 않습니다.

조회 조건을 SQL로 나타내면 다음과 같습니다. 현재의 단일 활성 스케줄러를 전제로 하며, 조회된 ID를 send 전에 처리 중 집합에 등록하는 절차도 유지합니다.

SELECT e.*
FROM payment_outbox e
WHERE e.status = 'PENDING'
  AND e.next_attempt_at <= CURRENT_TIMESTAMP(6)
  AND NOT EXISTS (
      SELECT 1
      FROM payment_outbox previous
      WHERE previous.payment_id = e.payment_id
        AND previous.event_sequence < e.event_sequence
        AND previous.status IN ('PENDING', 'BLOCKED')
  )
ORDER BY e.next_attempt_at, e.id
LIMIT 100;

이 SQL의 후보에서 현재 처리 중인 ID도 제외합니다. 선행 행을 찾는 서브쿼리에는 재시도 시각이나 처리 중 ID 제외 조건을 적용하지 않습니다. 백오프 중이거나 이미 send한 선행 행도 후속 발행을 막아야 하기 때문입니다. 전송 중인 행은 DB에서 PENDING으로 남고, ACK 이후 PUBLISHED 기록이 커밋돼야 다음 순번이 후보가 됩니다. 한 번의 조회에서도 결제별로 맨 앞의 미발행 이벤트만 선택됩니다.

전송 실패 후 재시도 시각을 저장하면 전역 처리 슬롯은 반환하지만, 그 결제의 후속 발행은 계속 보류합니다. 선행 행이 BLOCKED가 되어도 후속 행을 자동 통과시키지 않습니다. 원인을 해결하고 재발행해야 하며, 해당 결제의 대기 시간도 관측합니다. PENDING과 BLOCKED 행은 정리 대상에서 제외합니다. 조회 인덱스는 기존 (status, next_attempt_at, id)와 함께 선행 행 검색을 지원하는 (payment_id, event_sequence) 등을 실행 계획으로 확인해야 합니다.

이렇게 콜백으로 서로 다른 결제를 병렬 처리하면서, 같은 결제의 이벤트는 순서대로 제출할 수 있습니다. Kafka key만으로 해결되는 부분과 Relay 조회 정책으로 보장해야 하는 부분을 나눈 것입니다.

폴링 주기와 처리 슬롯을 따로 관리한다

스케줄러는 매 실행에서 남은 슬롯만큼 조회하고 비동기 전송을 등록한 뒤 반환합니다. 콜백은 슬롯을 반환할 뿐 새 조회를 직접 시작하지 않습니다. 다음 fixedDelay 실행이 그 슬롯을 사용합니다. DB 트리거나 CDC 없이도 동작하며, 100ms는 이벤트 발견을 위한 조회 간격 후보입니다. send 등록과 조회 시간은 실제 시작 간격에 더해집니다.

슬롯이 없으면 DB 조회를 생략합니다. 빈 조회만 있다고 보면 명목상 5초 간격은 Relay 하나당 초당 0.2회, 100ms는 초당 10회입니다. 주기를 줄이면 발견 대기는 줄지만 조회 비용이 증가하므로 반영 지연과 DB 부하를 함께 봅니다.

CDC로 전환하기 전에 현재 병목부터 구분해야 한다

CDC를 사용하더라도 결제 결과와 Outbox를 같은 트랜잭션에 저장하는 구조는 유지합니다. 달라지는 것은 발행 경로입니다. Relay가 PENDING을 주기적으로 조회하는 대신, Debezium이 MySQL binlog에 기록된 Outbox INSERT를 읽어 Kafka로 전달합니다.

이번에 먼저 줄일 수 있었던 것은 5초 조회 간격에서 생기는 발견 대기와, 배치 전체의 전송과 결과 기록을 기다리는 대기였습니다. 조회 주기를 줄이고 완료된 건부터 기록해 슬롯을 반환하도록 바꾸면 현재 Relay에서도 이 두 구간을 줄일 수 있었습니다. 앞서 본 약 200ms의 반영 지연도 조회 주기를 조정한 뒤의 결과입니다. 이 상황에서는 발행 경로 전체를 CDC로 바꾸기 전에 현재 구현의 대기를 해소하는 쪽을 선택했습니다.

CDC로 바꿨을 때 모든 구간이 함께 빨라지는 것도 아닙니다.

지연 구간 CDC로 전환했을 때
Outbox INSERT → 발행 대상 발견 주기적 SELECT 대기를 없앨 수 있지만, 커넥터의 binlog 읽기와 큐 대기가 생깁니다.
Kafka 전송 → ACK 브로커 지연과 Kafka의 전송 용량은 계속 영향을 줍니다.
Kafka 수신 → 주문 DB 커밋 Consumer 적체와 주문 DB의 처리 속도는 별도로 개선해야 합니다.

기존 Outbox의 재시도 계약도 그대로 옮겨지지 않습니다. 현재 Relay는 next_attempt_at을 확인해 발행 시점을 정하고, 전송 결과에 따라 PUBLISHED나 BLOCKED를 기록합니다. 반면 표준 Outbox Event Router는 INSERT 중심으로 동작하며 UPDATE를 발행 재시도로 해석하지 않습니다. 따라서 CDC가 INSERT를 읽는 시점에는 기존 행의 next_attempt_at이 발행을 제어하지 않고, Kafka로 전달됐다고 DB의 PUBLISHED가 자동 갱신되지도 않습니다. 전환하려면 행별 재시도와 수동 재발행, 발행 상태 조회, 정리 기준을 커넥터의 전달 상태와 맞춰 다시 설계해야 합니다. 상태 컬럼이 있다고 CDC를 쓸 수 없는 것은 아니지만, 커넥터를 연결하는 것만으로 현재 동작이 유지되지는 않습니다. Outbox Event Router의 동작 계약

복구의 기준도 달라집니다. Polling Relay는 DB에 남은 미완료 행을 다시 조회하지만, CDC는 저장된 binlog 위치나 GTID에서 읽기를 재개합니다. 커넥터 중단이 길어져 필요한 binlog가 삭제되면 재스냅샷 등 복구 절차가 필요하므로, 커넥터의 최대 중단 시간을 고려한 binlog 보존과 Outbox 정리 정책을 함께 정해야 합니다. CDC로 바꿔도 HTTP와 이벤트의 중복 적용을 막는 Consumer 계약은 그대로 필요합니다. MySQL 커넥터의 재시작과 장애 복구

현재는 짧은 폴링과 슬롯 제한으로 전달 지연을 조정할 수 있는 범위를 먼저 개선했습니다. 이후에는 조회 쿼리의 DB 비용이 커지는지, 발견 대기가 주문 반영 지연의 주된 부분으로 남는지를 기준으로 CDC를 다시 검토할 수 있습니다.

6. 중복과 순서 역전을 구분해 주문에 반영해야 한다

Outbox로 전달할 일을 보존하면 재발행도 발생합니다. Kafka가 ACK를 반환한 뒤 Relay가 PUBLISHED를 저장하기 전에 종료되면, 다음 Relay는 같은 행을 다시 보내게 됩니다. 정상 HTTP 응답과 Kafka 이벤트가 모두 도착하는 경우도 있습니다.

따라서 주문 반영에서는 수신 여부와 업무 적용 여부를 구분합니다. eventId가 이미 저장되어 있더라도, 선행 결과를 기다리는 이벤트라면 아직 처리가 끝난 것이 아닙니다.

HTTP와 이벤트는 같은 결제 결과 적용 경로를 사용합니다. HTTP 응답에도 paymentId와 paymentAttemptId, eventSequence를 전달하고, (payment_id, event_sequence)별 적용 이력과 마지막 적용 순번을 주문 DB에 기록합니다. 같은 결제의 적용은 순번 관리 행을 잠그는 등으로 직렬화합니다. 이력의 존재 확인과 주문 변경을 서로 다른 TX로 나누면 두 요청이 동시에 “아직 반영되지 않았다”고 판단할 수 있습니다. 적용 이력 INSERT, 주문 상태 변경, 마지막 적용 순번 갱신은 같은 주문 TX에서 커밋해야 합니다. 적용 이력에는 (payment_id, event_sequence)의 유일성 제약을 둡니다. HTTP가 먼저 반영한 승인이라면 Kafka에서 다시 승인 이벤트를 받아도 업무 변경을 반복하지 않고 수신 이력만 남깁니다. eventId만으로는 HTTP와 이벤트의 중복을 막을 수 없습니다. HTTP에 eventId가 없더라도 같은 확정 결과를 식별할 수 있는 키가 필요하기 때문입니다.

먼저 반영한 경로 뒤에 도착한 경로 주문 TX의 판단
승인 HTTP 응답 같은 승인의 Kafka 이벤트 같은 결제와 순번의 적용 이력이 있으므로 주문 변경을 반복하지 않음
승인 Kafka 이벤트 늦게 도착한 승인 HTTP 응답 같은 적용 이력으로 중복 반영을 막음
첫 번째 부분 환불 결과 다른 refundId의 두 번째 부분 환불 결과 다른 결과이므로 순번과 금액을 검증한 뒤 별도 반영

같은 결과 키로 들어온 금액과 통화, 원주문 연결이 기존 기록과 다르다면 정상 중복으로 숨기지 않고 충돌로 분리해야 합니다. 재전달 계약은 “같은 ID이면 무조건 무시”가 아니라 같은 ID로 같은 확정 사실이 다시 온다는 전제 위에 있습니다.

승인을 아직 반영하지 못했다면 취소 결과를 보관해야 한다

Relay의 순서 제한은 신규 발행의 추월을 막습니다. 그래도 기존에 발행된 메시지나 별도 수동 복구 경로로 취소 결과가 먼저 들어올 수 있습니다. 주문 DB에 승인 적용 이력이 없다는 이유로 취소 이벤트를 버리면 복구할 근거까지 잃습니다. Consumer의 책임은 이미 완료된 PG 취소를 주문에 반영하는 것이며, PG 취소를 다시 호출하는 것이 아닙니다.

예를 들어 마지막 적용 순번이 0인데 취소 완료 sequence=2가 도착했다면, payload와 eventId와 paymentId, 순번을 inbox에 WAITING_FOR_PREDECESSOR로 저장합니다. 이것은 취소 처리가 완료됐다는 표시가 아니라, 선행 결과가 없어 보류 중이라는 기록입니다. DB 저장도 실패했다면 offset을 넘기지 않습니다.

보류 기록의 DB 커밋이 끝난 뒤에는 Kafka offset을 커밋할 수 있습니다. 그 대신 이후 처리 책임을 DB에서 다시 조회할 수 있는 복구 작업자가 맡아야 합니다. Kafka 자동 커밋을 끄고 DB 커밋 이후 offset이 처리되도록 설정합니다. 같은 파티션에서 취소 이벤트만 붙잡고 재시도하면 그 뒤에 있는 승인 이벤트를 읽지 못할 수 있으므로, 선행 결과의 도착을 기다리는 일은 이 보류 저장소로 넘깁니다. Spring Kafka의 offset 커밋 방식

이후 승인 sequence=1이 도착하면 승인 사실을 기록하고, 저장된 취소 sequence=2까지 연속으로 적용합니다. 보류 이벤트를 다시 확인하는 복구 작업자도 프로세스 재시작 후 동작해야 합니다. 이미 보관된 연속 결과가 있다면 두 결과와 주문 변경을 같은 주문 TX에서 반영해 커밋 시점에는 해당 취소 결과까지 반영된 상태를 남깁니다. 판매자 알림도 중간의 수락 대기 상태가 아니라 커밋된 주문 상태를 기준으로 결정합니다. HTTP로 승인 1이 이미 적용되어 있다면 취소 2는 바로 처리할 수 있습니다.

업무 적용 때는 orderId와 paymentId, paymentAttemptId, orderAdjustmentId의 연관 관계를 확인하고, 환불 결과의 업무 중복은 refundId로도 차단합니다. 같은 원거래의 두 번째 부분 환불을 첫 번째와 같은 작업으로 오인하지 않아야 합니다. 일부 메뉴만 취소됐다면 해당 주문 항목의 수량과 환불액만 반영하고, 나머지 주문의 조리와 제공은 유지합니다. 주문 전체 취소와 결제의 부분 환불 상태를 같은 상태값으로 덮어쓰지 않습니다. 재고 복구도 취소 금액으로 수량을 역산하지 않고 주문 변경 내역의 대상 수량과 조리 상태를 기준으로 결정합니다. 선행 결과를 찾지 못한 이벤트는 처리 대기 시간과 누락 순번을 드러내고, 결제 서비스의 불변 결과 내역과 대조해 복구합니다. 단순히 가장 큰 순번만 저장하고 이전 이벤트를 모두 버리면 필요한 승인과 환불 이력까지 빠질 수 있습니다.

취소 요청이 이미 기록된 주문에서는 승인 사실을 이력에 남기더라도 판매자 수락 대기로 전환하지 않습니다. 이미 취소된 주문에 늦은 승인이 도착해도 수락 대기로 되돌리지 않습니다. 주문의 현재 상태와 결제 결과의 적용 이력을 함께 확인합니다. 실패 시 재고 해제와 조리 전 취소와 환불의 재고 복구도 해당 예약의 처리 이력으로 중복을 막습니다. 조리 완료 후 금액 보상은 판매 가능한 수량 복구와 구분합니다.

7. 관측하기

사이드 프로젝트에서 축제 계약을 확보하는 일은 중요한 과제였습니다. 계약 이후에는 행사 시간 동안 결제가 안정적으로 처리되고, 결제를 마친 주문을 판매자가 제때 확인할 수 있어야 했습니다. 현장에서의 결제와 주문 경험이 다음 축제에서도 서비스를 사용할지 판단하는 근거가 되기 때문입니다.

별도 운영 인력을 충분히 두기 어려운 만큼, 문제가 생길 때마다 개발자가 로그부터 뒤지는 방식으로는 대응이 늦어질 수 있었습니다. 그래서 결제가 진행 중인지, 승인은 끝났지만 주문 반영이 남았는지, 판매자가 수락하기를 기다리는지를 한 화면에서 구분할 수 있도록 백오피스를 구성했습니다. 운영 중인 사람이 문의 내용을 보고 어느 구간을 확인해야 할지 바로 알 수 있게 하는 것이 목적이었습니다.

결제 성공 로그만으로는 주문 반영 여부까지 알 수 없으므로, orderId → paymentAttemptId → eventId를 연결해 남아 있는 단계를 확인합니다.

상태 확인할 내용
PG 결과 확인 중 기존 결제 시도와 거래 결과 조회가 필요한가
결제 확정 후 주문 미반영 HTTP 또는 이벤트의 주문 반영이 남았는가
선행 결과 대기 어떤 paymentId의 몇 번째 결과가 없으며, 얼마나 기다렸는가
결제 확인 후 판매자 수락 대기 시스템 반영은 끝났고 판매자 응답을 기다리는가
조리 중, 준비 완료, 픽업 완료 판매자 수락 이후 조리와 제공 흐름은 정상인가

백오피스에서는 결제 승인 수와 주문 반영 완료 수, 처리 추이와 최근 주문을 함께 확인합니다. 정상 HTTP로 반영된 주문은 Outbox가 아직 PENDING이어도 미반영 주문이 아닙니다. 판매자가 수락하지 않은 정상 주문도 Relay 지연에 포함하지 않습니다. 미반영 주문 수와 가장 오래 기다린 시간과 함께 Outbox 대기 시간과 Kafka lag, DB 결과 기록 적체를 봅니다.

이후 주문 서비스와 결제 서비스의 DB까지 분리되고 백오피스의 통합 조회 비용이 커지면, 이벤트로 갱신하는 Materialized View 역할의 읽기 모델도 검토할 수 있겠습니다.

알림이 누락돼도 주문 조회로 확인할 수 있다면 알림용 Outbox까지 필수로 추가할 필요는 없습니다. 이번 문제에서 먼저 보장해야 했던 것은 주문이 결제 확인 후 수락 대기 상태에 도달하는 일이었습니다.

결제 결과를 저장한 것으로 고객의 주문 처리가 끝나지는 않습니다. 저장된 결과를 잃지 않고 전달하고, 주문에 한 번만 적용하고, 반영되지 않은 주문을 찾아 복구할 수 있어야 판매자가 주문을 받아 다음 업무를 이어갈 수 있습니다.
