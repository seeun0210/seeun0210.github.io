# Outbox 폴링 주기 비교의 측정 자료

이 자료는 로컬 HTTP 설계 프로토타입의 측정값입니다. 실제 운영 환경이나 실제 NICEPAY의 측정값이 아닙니다.

- Kafka broker/client 4.1.2, MySQL 8.4.13, Java 21.0.12.1, 단일 로컬 환경입니다.
- Kafka partition 3개, 복제 계수 1입니다.
- 클라이언트 → 주문 HTTP → 결제 HTTP → 모의 PG HTTP를 사용합니다. 각 서버는 같은 JVM에서 실행하며 DB 스키마와 연결, 트랜잭션을 분리했습니다.
- 비교한 Relay는 최대 100건을 모두 먼저 전송한 뒤 future를 수집하고 결과를 일괄 기록합니다. 콜백 Relay 성능이나 장애 복구 실험의 자료가 아닙니다.
- `fixedDelay`만 5,000ms와 100ms로 비교했습니다. 처음 실행도 각 delay 후입니다.
- 각 프로필과 조건에서 200건을 20건/초의 목표 유입으로 3회 실행했습니다. 총 18회 3,600건입니다.
- 응답 지연: 매 5번째 결제의 HTTP 응답을 결과 커밋 후 5초 지연시켜 4초 timeout을 넘깁니다.
- PG 지연: 모의 PG가 rolling 1초 호출 9건 초과에 3초 성공 응답 대기를 주입합니다. 실제 PG 한도를 뜻하지 않습니다.

## 측정 정의

`latency_ms`는 결제 결과와 Outbox COMMIT 완료를 애플리케이션이 확인한 시각부터 주문 COMMIT 완료 확인까지입니다. `request_to_order_ms`는 주문 HTTP 서버의 승인 처리 요청 수신부터 같은 주문 반영까지입니다. 같은 JVM의 `System.nanoTime()`을 사용합니다. 결제창 인증, 고객 화면 완료, 판매자 수락은 포함하지 않습니다.

각 실행의 분위수는 지연을 정렬한 뒤 `ceil(p × n)`번째 값을 선택합니다. 본문의 대표값은 세 실행의 분위수 중앙값이며 전체 표본을 합친 분위수가 아닙니다. 응답 지연 대상 EVENT는 실행당 40건입니다. `summary.json`에는 반복별 범위도 있습니다.

미반영 수와 가장 오래된 미반영 주문의 나이는 20ms 간격으로 관찰한 근사 최대치입니다. 완료 주문의 지연 분위수와 구분합니다. 모든 실행의 종료 시점에 broker_verified=200, db_verified=200, remaining_unapplied=0을 대조했습니다. 장기 운영 누락률이나 장애 내구성을 입증하지 않습니다.

`trials.jsonl`에는 HTTP 경로 결과와 전체 주문 반영 결과가 각각 한 줄씩 들어갑니다. 12줄이 12회 실행을 뜻하지 않습니다. 프로필당 6회이며 세 프로필에서 총 18회입니다. 초기 연결 풀 오류가 난 개발 실행과 smoke 데이터는 포함하지 않았습니다.

원래 실행 기록과 주문별 CSV를 보존한 것입니다. 매 실행은 새 JVM이며 DB·호스트 상태 등의 변동을 통제하지 않았으므로 정상 경로의 작은 차이나 개선 폭 전체의 단일 원인을 확정하지 않습니다.
